# Dynamic Allocation Issues
# 动态分配问题

Valgrind 的 Memcheck 工具在查找与**动态分配**相关的问题时非常有用——无论是 C 中的 `malloc` 和 `free`，还是如果你以后学习 C++，其中的 `new`/`new[]` 和 `delete`/`delete[]`。与其他内存区域一样，Memcheck 会显式跟踪哪些地址有效、哪些无效。它还会精确跟踪 `malloc`、`new` 和 `new[]` 返回了哪些指针，并在已分配块的**两侧**放置一些无效空间。

基于所有这些信息，Memcheck 可以报告各种各样的问题。首先，如果访问刚好越过动态分配数组的末尾，Memcheck 能检测到这个问题。其次，Memcheck 能检测**双重释放**指针、释放错误的指针，以及分配与释放之间的不匹配（例如，`delete` 由 `malloc` 分配的内存，或把 `delete[]` 与 `delete` 弄混，这对 C++ 程序员来说会是错误）。例如，假设我们编写了以下（显然有 bug 的）代码：

```c
int * ptr = malloc(sizeof(int));
ptr[1] = 3;
```

如果我们在 Memcheck 中运行它，它会报告以下错误：

```text
==5465== Invalid write of size 4
==5465==    at 0x40054B: main (outOfBounds.c:8)
==5465==  Address 0x51fc044 is 0 bytes after a block of size 4 alloc'd
==5465==    at 0x4C2AB80: malloc (in /usr/lib/valgrind/vgpreload_memcheck-amd64-linux.so)
==5465==    by 0x40053E: main (outOfBounds.c:7)
```

错误首先告诉我们问题（我们进行了一次大小为 4 字节的无效写入），并给出一个栈跟踪，指出该无效写入发生的位置（在 `main` 中，文件 `outOfBounds.c` 的第 8 行）。第二部分告诉我们程序试图访问的无效地址以及最近的**有效位置**。在这个例子中，它报告为“**0 bytes after**”（即位于有效区域之后的第一个无效字节）“**a block of size 4**”（即该有效区域分配了多少空间）。然后 Memcheck 报告那块有效内存是在哪里分配的（在 `main` 中第 7 行，通过调用 `malloc`）。

注意，如果我们最近释放了一块内存，Memcheck 会报告与该内存块的**邻近关系**，即使它已经不再有效。例如，如果我们写：

```c
int * ptr = malloc(sizeof(int));
free(ptr);
ptr[0] = 3;
```

那么 Memcheck 会报告该无效写入位于**已释放的块内部**（并告诉我们是在哪里释放该块的）：

```text
==5486== Invalid write of size 4
==5486==    at 0x4005A3: main (outOfBounds2.c:9)
==5486==  Address 0x51fc040 is 0 bytes inside a block of size 4 free'd
==5486==    at 0x4C2BDEC: free (in /usr/lib/valgrind/vgpreload_memcheck-amd64-linux.so)
==5486==    by 0x40059E: main (outOfBounds2.c:8)
```

Valgrind 的 Memcheck 还会检查**内存泄漏**。然而，默认情况下它只报告泄漏的**摘要**，这对查找和修复问题没有太大帮助。如果你有内存泄漏，你会想使用 `--leak-check=full` 选项运行。这样，Memcheck 会报告每一个未被释放的分配的位置。然后你可以用这些信息来弄清楚应该在哪里释放那块内存。

注意，当把 Valgrind 的 Memcheck 与 GDB 一起运行时，你可以随时用 monitor 命令 `monitor leak_check full reachable any` 来运行泄漏检查器。
