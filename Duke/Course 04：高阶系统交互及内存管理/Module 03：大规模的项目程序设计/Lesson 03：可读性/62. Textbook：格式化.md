# Formatting
# 格式化

代码的**格式化**也会对其可读性产生很大影响。程序员在很大程度上同意一些基本规则。一条常见的规则是，代码应该根据**块结构**进行缩进——也就是说，在 C 中，位于更多花括号内部的代码应该比位于更少花括号内部的代码缩进更多。另一条规则是，通常应该在语句末尾放置一个换行符，以便连续的语句出现在不同的行上。

然而，程序员通常对代码格式化的具体细节有很大分歧。也许最有争议的话题是**花括号的位置**。下面的代码展示了四种不同的花括号放置约定：Java 风格、1TBS、Allman 风格和 GNU 风格。我们要注意，其中许多风格还有其他变体，通常涉及 `else` 是否“**依偎**”相应 `if` 的右花括号（即 `else` 与右花括号在同一行），和/或单行块周围是否使用花括号。当然，这里没有展示其他风格。

```c
// Java style
int sumNums (int n) { 
  int total = 0;
  for (int i = 0; i < n; i++) {
    total = total + n;
  }
  return total;
}

// 1TBS
```

我们**强烈偏好**所谓的“**Java**”风格（之所以这样命名，是因为 Sun 的风格指南使用了它，因此许多 Java 代码都使用它），原因有几个。首先，把左花括号放在它所从属的 `if/else/for/…` 的同一行，有助于避免程序员意外地向函数体添加了一行代码，但错误地把它放在花括号之前的情况。要看到这个问题，考虑以下代码：

```c
if (hasPrivileges (user))
  logActivity(user,action);  // 意外添加到了错误的位置
{
  someSecureActivity(action);
}
```

这里有人添加了代码——一个记录某些活动的函数调用——意图把它写在 `if` 的函数体中，但把花括号与 `if` 分开了。在这种情况下，`logActivity` 调用就是 `if` 函数体的全部，其余代码是合法的，但**不受 `if` 的条件保护**。也就是说，代码的行为就像它是：

```c
if (hasPrivileges (user)) {
  logActivity(user,action);
}
someSecureActivity(action);
```

这样的错误可能导致软件中的严重错误。在这个假设的例子中，这个错误几乎肯定会成为一个**安全漏洞**，允许任何用户执行特权操作（更糟的是，如果用户没有执行该操作的权限，就不会记录活动）。

我们偏好 Java 风格而不是 1TBS，主要是从**一致性**的角度（花括号相对于其余代码总是处于相同位置）。也许最重要的是，我们推荐一种花括号风格：**始终使用花括号**，即使它们在单行块周围可以省略。省略它们会使引入错误更容易。

最终，你使用什么花括号风格，要么由你工作地点的风格指南决定，要么留给你个人选择。
