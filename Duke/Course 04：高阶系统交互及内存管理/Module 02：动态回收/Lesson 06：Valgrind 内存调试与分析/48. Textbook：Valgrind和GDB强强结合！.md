# Valgrind with GDB
# 将 Valgrind 与 GDB 结合使用

我们可能会遇到一个问题：它出现在某一行代码上，但只在特定情况下出现，而该行代码前几次执行时并不会显现。当这种情况发生时，我们可能会发现调试代码更加困难，因为仅仅在出问题的行上设置断点可能无法给我们足够的信息——我们可能不知道何时在正确的条件下到达该断点。我们想要的是能够**同时运行 GDB 和 Valgrind**，并让 Valgrind 在遇到错误时告诉 GDB，把控制权交给 GDB。

幸运的是，我们完全可以做到这一点。如果我们用选项 `--vgdb=full --vgdb-error=0` 运行 Valgrind，那么 **Valgrind 会在遇到第一个错误时停止，并把控制权交给 GDB**。需要一些协调才能让 GDB 连接到 Valgrind（它们作为独立进程运行）；然而，用这些选项运行时，Valgrind 会给出我们需要传递给 GDB 的信息，以实现这一点：

```text
==24099== (action at startup) vgdb me ...
==24099==
==24099== TO DEBUG THIS PROCESS USING GDB: start GDB like this
==24099==   /path/to/gdb ./a.out
==24099== and then give GDB the following command
==24099==   target remote | /usr/lib/valgrind/../../bin/vgdb --pid=24099
==24099== --pid is optional if only one valgrind process is running
```

此时，Valgrind 已经启动了程序，但还没有进入 `main`——它正在等待你启动 GDB 并将它连接到 Valgrind。我们可以通过运行 GDB（在另一个终端或 Emacs 缓冲区中），然后把 Valgrind 给我们的 `target` 命令复制粘贴到 GDB 的命令提示符中来实现：

```text
(gdb) target remote | /usr/lib/valgrind/../../bin/vgdb --pid=24099
Remote debugging using | /usr/lib/valgrind/../../bin/vgdb --pid=24099
relaying data between gdb and process 24099
Reading symbols from /lib64/ld-linux-x86-64.so.2...Reading symbols from ...
done.
Loaded symbols for /lib64/ld-linux-x86-64.so.2
0x00000000040012d0 in _start () from /lib64/ld-linux-x86-64.so.2
(gdb)
```

此时，我们可以给 GDB 我们想要的命令。最常见的是，我们会想给 GDB `continue` 命令，**它会让它运行，直到 Valgrind 遇到错误**。此时，Valgrind 会中断程序并把控制权交还给 GDB。现在你可以给 GDB 任何你想要的命令，以便检查程序的状态。

Valgrind 和 GDB 的结合相当强大，并且让你能够通过 `monitor` 命令运行一些新命令。例如，如果我们正在调试与指针相关的错误，并想知道哪些变量仍然指向某个特定的内存位置，我们可以使用 `monitor who_points_at` 命令来做到这一点：

```text
(gdb) monitor who_points_at 0x51fc040
==24303== Searching for pointers to 0x51fc040
==24303== *0xfff000450 points at 0x51fc040
==24303==  Location 0xfff000450 is 0 bytes inside local var "p"
==24303==  declared at example.c:6, in frame #0 of thread 1
```

Memcheck 还有许多其他可用的 `monitor` 命令。参见  
http://valgrind.org/docs/manual/mc-manual.html#mc-manual.monitor-commands  
以获取有关可用 `monitor` 命令及其参数的更多信息。
