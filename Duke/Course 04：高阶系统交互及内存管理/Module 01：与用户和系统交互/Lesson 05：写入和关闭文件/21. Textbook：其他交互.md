# Other Interactions
# 其他交互

有时程序会以读取或写入文件之外的方式与系统其余部分或外部世界交互。UNIX 试图让尽可能多的这类访问类型在合理范围内**看起来类似于访问文件**——呈现相同的接口，从而允许使用熟悉的函数来执行这些操作。对于符合这种模型的操作，发起访问的底层**系统调用**会返回一个**文件描述符**，然后它被传递给其他适当的系统调用（例如 `read` 或 `write`）。如果用户想使用 `stdio` 中的 IO 函数（`fprintf`、`fgets`、`fgetc`……），她可以使用 `fdopen` 库调用来获得与文件描述符对应的 `FILE *`。

一个“看起来像文件”的交互例子是从用户读取输入并打印到终端。你已经用 `printf` 向终端打印过东西，它把输出打印到 `stdout`，一个连接到“**标准输出**”的 `FILE *`。默认情况下，标准输出是终端；然而，正如你在课程 2 中学到的，你可以重定向输出，使其改为写入实际文件。你也可以使用 `fprintf` 打印到 `stderr`，它是另一个默认也去终端的 `FILE *`。虽然 `stdout` 和 `stderr` 默认都打印到终端，但它们服务于不同的目的：一个用于**输出**，另一个用于**错误**。[1] 你也可以通过从 `stdin` 读取来从终端读取用户输入。这些 `FILE *` 每一个都在 `stdio.h` 中声明。当你的程序启动时，它们都是打开的（C 库在 `main` 之前打开它们），它们对应于文件描述符 `0`（`stdin`）、`1`（`stdout`）和 `2`（`stderr`）。你**永远不应该关闭这些 `FILE *`**，因为 C 库负责它们，而不是你的代码。

另一个“看起来像文件”的交互例子是**跨网络传输数据**。程序通过 `socket` 系统调用获得一个**套接字**（socket）的文件描述符——套接字是数据传输的逻辑抽象。根据程序想要的网络协议，可能还需要额外的设置来指定目的地、建立连接等。然而，一旦套接字设置好，就可以使用 `write` 系统调用通过套接字发送数据，或使用 `read` 系统调用从网络读取数据（如果没有收到数据，它会**阻塞**——使程序等待——直到数据到达）。当然，如果已经使用 `fdopen` 系统调用设置了 `FILE *`，那么就可以使用 `fprintf` 或 `fgets` 之类的库函数（它们对底层文件描述符进行 `write` 和 `read` 系统调用）。

另一种看起来像文件的交互形式是**管道**（pipe）。这个名字可能听起来耳熟，因为 shell 中有一个同名的构造（例如 shell 中的 `cmd1 | cmd2`），它使用这种通信类型。管道是两个进程之间的**单向通信通道**。一个进程把数据写入管道的一端，另一个进程从管道读取，获得第一个进程写入的数据（如果没有数据可用则阻塞）。这种通信对每个进程来说看起来完全像读/写文件（因为它们同样读/写文件描述符，或使用这样做的库函数）。当你使用管道操作符时，shell 会使用它：它建立一个管道，并安排第一个进程的标准输出文件描述符为管道的写入端，第二个进程的标准输入文件描述符为管道的读取端。

UNIX 提供访问非传统文件之物的另一种方式，是通过**设备特殊文件**（device special files）。这些在文件系统中表现为文件（例如你可以用 `ls` 看到它们），但有一个特殊的文件类型，表明操作系统不应尝试从磁盘（或其他介质）读取/写入数据，而应执行特殊功能。这些文件通常位于 `/dev` 目录中。

例如，在 Linux 上，“文件” `/dev/random` 提供对内核提供的**安全伪随机数生成器**的访问。你可以用 `fopen`（或 `open`）打开这个文件进行读取，并用你喜欢的任何方法从中读取。然而，当你对这个文件执行读取时，内核识别出它应该执行随机数生成例程来提供数据，而不是读取磁盘。内核会按照它的算法生成随机数，并把它作为系统调用读取的数据返回。如果内核的**熵**（entropy）模型表明它需要更多熵来安全地生成数字，读取操作可能会阻塞。[2] 可以改用 `/dev/urandom` 设备，用相同的算法生成数字，但不考虑是否有足够的熵可用于安全敏感目的。

然而，有些东西不适合“**一切都是文件**”模型。这些通常由系统调用处理，但可能不涉及文件描述符。例如，如果你需要程序确定当前时间，你可以使用 `gettimeofday` 系统调用，它只返回当天时间。还有创建新进程（`fork`）、用另一个程序替换当前运行程序（`execve`）、退出当前程序（`exit` 是通常用于此目的的库调用，`_exit` 提供对底层系统调用的访问，很少需要），以及许多其他事情的系统调用。事实上，有几百个系统调用。随着你积累编程经验，它们会对你越来越熟悉。

另一种交互形式是操作系统需要**异步**地通知程序某些事情——不是在程序显式请求的时候，而是在其执行期间的任何时间。这里，与系统调用不同，是操作系统发起与程序的通信。UNIX 风格的操作系统支持许多**信号**（每个信号有一个编号和一个符号名，表示它代表什么）。

大多数信号默认对程序是**致命的**——如果操作系统需要向程序传递一个致命信号，它会杀死相关程序。我们已经见过一个致命信号的例子——尽管我们没有把它作为信号来讨论。当你的程序发生**段错误**时（当你的程序以某些无效方式访问内存时会发生），操作系统向它发送 `SIGSEGV`，杀死程序。其他一些信号的默认动作是**被忽略**，在这种情况下，如果操作系统传递该信号，什么也不会发生。

程序可以改变每个特定信号发生的情况（除了信号 9，即 `SIGKILL`，它总是致命的）。信号新行为的一个选项是让操作系统使程序运行一个特定函数（程序在发出请求操作系统修改该信号行为的系统调用时指定哪个函数）。我们这里不深入信号、信号处理及相关主题的细节，但你至少应该知道它们存在，并预期将来会学习它们。我们要注意，因为程序无法工作（它不断发生段错误）就设置程序直接忽略 `SIGSEGV` 是一个**坏主意**——记住，你永远不想隐藏错误，你总是想修复它。

[1] 如果你想重定向其中一个而不重定向另一个，这种区分可能非常有用：例如，你可能想把输出写入文件，但在运行程序时立即在终端上看到任何错误。

[2] 内核通常通过跟踪它所能观察到的、难以预测的事件信息来生成熵（例如内核必须处理的硬件事件之间的微秒数，如按键、鼠标移动，或通过网络接口到达的数据），然后以此作为伪随机数生成的基础。随着数字的生成，如果没有新的难以预测的事件来馈送算法，就可能猜测出模式的信息，所以内核会等待更多这样的事件，然后才提供更多数字。
