# Past Versions
# 过去的版本

大多数版本控制系统的基本原理是：你把工作**提交**（commit）到版本控制系统中，然后它会保留你该版本工作的**快照**（snapshot）。提交时，你写一条**日志条目**（log entry），描述你做了什么。之后，你可以查看日志，并在需要时回到工作的旧版本。例如，如果你决定重写一段代码来改进它，结果却发现反而破坏了程序，你可以回到之前可工作的版本。

针对这个问题，“**新手工具**”式的做法是保留工作的副本，并手工管理它们。你可能会想：“好吧，我可以在开始之前复制所有代码，然后如果需要就用那个副本。”如果你有意识地意识到自己即将进行有风险的代码重写，你可能会采取这种做法。然而，如果你开始修改代码，之后才意识到麻烦呢？如果你使用版本控制系统，就应该**定期提交**，因此过去会有良好的修订版本。此外，如果你手动定期复制，你会发现很难手工管理所有副本。

像 Git 这样的版本系统还有处理过去版本的出色工具。例如，Git 有一个名为 `bisect` 的命令，可以让你搜索过去是在哪里弄坏东西的。假设我知道某个功能 6 个月前还能工作；但今天运行一些测试后，意识到该功能坏了。我想回去准确找出哪个版本破坏了这个功能，看看那个版本改了什么，然后修正代码。`bisect` 命令让 Git 帮我搜索第一个出问题的版本。

具体来说，`bisect` 在修订版本之间进行**二分搜索**（因此得名），以找到问题发生的位置。你可以通过告诉 Git 它访问的每个修订版本是好是坏来手动引导搜索，也可以提供一个 shell 脚本，让 Git 判断修订版本是否正确或有坏，从而**全自动**执行搜索。

版本控制不仅限于代码，事实上，它对任何大型协作项目（甚至只是小规模管理你自己的数据）都非常有用。为了给出 `bisect` 的一个具体例子，我们用 Git 对本专项课程的**所有材料**进行版本控制——包括 LaTeX 源码、代码示例、动画和视频录制。其中一个动画被无意中删除了，我们需要从最近的版本恢复它。写一个 shell 脚本来测试该文件是否存在，然后运行 `git bisect`，在几秒钟内就找到了删除该文件的修订版本，并让我们从上一个修订版本恢复了它（并确保我们拥有最新版本！）。
