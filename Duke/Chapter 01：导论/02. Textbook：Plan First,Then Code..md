


Many novice programmers attempt to dive right into writing the code (in the programming language) as the first step. However, writing the code is actually a much later step in the process. A good programmer will plan first and write second, possibly breaking down a large programming task into several smaller tasks in the process. Even when cautioned to plan first and code second, many programming students ignore the advice—after all, why “waste” 30 minutes planning when you are time-crunched from all the work you have to do. This tradeoff, however, presents a false economy—30 minutes planning could save hours of trying to make the code work properly. Well planned code is not only more likely to be correct (or at least closer to correct), but is also easier to understand—and thus fix. To try to better understand the importance of planning before you write, imagine an analogy to building a house or sky scraper. If you were tasked with building a sky scraper, would you break ground and start building right away, figuring out how the building is designed as you go? Hopefully not. Instead, you (or an architect) would design blueprints for the building first. These blueprints would be iteratively refined until they meet everyone’s specifications—they must meet the requirements of the building’s owner, as well as be possible to build reasonably. Once the blueprints are completed, they must be approved by the local government. Actual construction only begins once the plans are fully completed. Programming should be done in a similar manner— come up with a complete plan (algorithm) first and build (implement in code) second. We said that the heart of programming is to figure out how to solve a class of problems— not just one particular problem. The distinction here is best explained by an example. Consider the task of figuring out if a particular number (e.g., 7) is prime. With sufficient knowledge of math (i.e., the definition of a prime number and the rules of division), one can solve this problem—determining that 7 is in fact prime. However, a programming problem typically looks at a more general class of problems. We would typically not write a program to determine if 7 is prime, but rather a program which, given a number N, determines if N is prime. Once we have an algorithm for this general class of problems, we can have the computer solve any particular instance of the problem for us. When we examine a class of problems, we have parameters which tell us which particular problem in the class we are solving. In the previous example, the class of problems is parameterized by N—the number we want to test for primality. To develop an algorithm for this class of problems, we must account for all possible legal values of the parameters. As we will see later, programming languages let us restrict what type of information a parameter can represent, to limit the legal values to those which make sense in the context of the problem. For primality testing, we would want our parameter N to be restricted such that it can only hold integer numbers. It would not make any sense to check if letters, words, or files are prime. 2/2 To write a program which takes any number N and determines if N is prime, we must first figure out the algorithm for this class of problems. As we said before, if we attack the problem by blindly writing code, we will end up with a mess—much like constructing a sky scraper with no plan. Coming up with the appropriate algorithm for a class of problems is a challenging task, and typically requires significant work and thought.

许多程序员新手都试图在第一步就直接开始编写代码（编程语言）。然而，编写代码实际上是整个过程中更晚的一步。优秀的程序员会先计划，后写代码，可能会在这个过程中将一个大型编程任务分解成几个较小的任务。即使被提醒要先计划后编码，许多编程学生也会忽视这一建议--毕竟，当你有很多工作要做而时间紧迫时，为什么还要 "浪费 "30 分钟来计划呢？然而，这种取舍带来的是虚假的经济效益，30 分钟的规划可以节省数小时的时间来使代码正常工作。计划周密的代码不仅更有可能正确（或至少更接近正确），而且更容易理解，从而更容易修复。

为了更好地理解编写前计划的重要性，请想象一下建造房屋或空中铲运机的比喻。如果你的任务是建造一座天车，你会立即破土动工，边做边想大楼是如何设计的吗？希望不会。相反，你（或建筑师）会先设计建筑蓝图。这些蓝图会反复推敲，直到符合每个人的规格要求--它们必须满足建筑物所有者的要求，并且能够合理地建造。蓝图完成后，必须得到当地政府的批准。只有在图纸全部完成后，才能开始实际施工。编程也应该以类似的方式进行--首先提出完整的计划（算法），其次才是构建（用代码实现）。

我们说过，编程的核心是找出如何解决一类问题，而不仅仅是一个特定的问题。这里的区别最好通过一个例子来解释。考虑一下找出一个特定数字（如 7）是否是质数的任务。只要有足够的数学知识（即质数的定义和除法规则），就能解决这个问题--确定 7 实际上是质数。然而，编程问题通常关注的是一类更为普遍的问题。我们通常不会编写一个程序来确定 7 是否是质数，而是编写一个程序，在给定一个数字 N 的情况下，确定 N 是否是质数。一旦我们掌握了这一类问题的算法，就可以让计算机为我们解决任何特定的问题实例。

当我们研究一类问题时，我们有参数来告诉我们要解决该类问题中的哪个特定问题。在前面的例子中，这一类问题的参数是 N，即我们要检验原始性的数字。要为这一类问题开发算法，我们必须考虑到参数的所有可能合法值。正如我们稍后将看到的，编程语言可以让我们限制参数所能代表的信息类型，从而将合法值限制在对问题有意义的范围内。对于原始性测试，我们希望参数 N 被限制为只能表示整数。检查字母、单词或文件是否为素数是毫无意义的。

要编写一个程序，接收任意数字 N 并确定 N 是否是素数，我们必须首先找出这类问题的算法。正如我们之前所说，如果我们盲目地编写代码来解决这个问题，最终结果将是一团糟--就像在没有计划的情况下建造一个天空刮板一样。为一类问题找出合适的算法是一项具有挑战性的任务，通常需要大量的工作和思考。
