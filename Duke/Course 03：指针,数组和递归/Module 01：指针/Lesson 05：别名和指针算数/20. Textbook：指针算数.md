# Pointer Arithmetic
# 指针算术

像 C 中的所有类型一样，指针也是具有数值的变量。早慧的编程学生可能会想，变量的值是否可以像操作整数和浮点数的值那样被操作。答案是响亮的**可以**！

考虑以下代码：

```c
int x = 4;
float y = 4.0;
int *ptr = &x;

x = x + 1;
y = y + 1;
ptr = ptr + 1;
```

第 1–3 行初始化了三个不同类型的变量（整数、浮点数和指向整数的指针）的值。第 5–7 行给每个变量加 1。对于每种类型，加 1 有不同的含义。对于 `x`，加 1 执行整数加法，结果是 `5`。对于 `y`，加 1 需要把 `1` 转换为浮点数（`1.0`），然后执行浮点加法，结果是 `5.0`。对于整数和浮点数，加 1 的基本语义都是“大 1”。对于整数指针 `ptr`（最初指向 `x`），加 1 的语义是“**内存中后一个整数**”。递增指针应该让它指向内存中的“下一个”整数。为了做到这一点，编译器生成的指令实际上是加上一个整数在内存中占用的字节数（例如，`+1` 意味着把指针的数值改变 `+4`）。同样，当给指向任何类型 `T` 的指针加上 `N` 时，编译器生成的指令会把 `(N * 类型 T 的值的字节数)` 加到指针的数值上——使它指向内存中更后面的 `N` 个 `T`。这就是为什么指针算术不能用于指向 `void` 的指针；因为编译器不知道一个“东西”有多大，它不知道如何做数学来移动 `N` 个“东西”。

就编译器而言，我们这里写的代码是合法的，然而，我们在这个上下文中使用指针算术是相当**无意义**的。特别是，当这段代码结束时，我们不知道 `ptr` 实际指向哪个盒子。如果我们还有一行代码执行 `*ptr = 3;`，代码仍然会编译，但会有**未定义行为**（undefined behavior）——我们无法手工执行它并确定地说会发生什么。具体来说，当 `ptr = &x` 时，它指向一个（整数的）盒子，而这个盒子是孤立的——它不是某个由多个整数盒子组成的序列的一部分（我们很快就会看到）。递增指针会让它指向内存中的某个位置，我们只是不知道是哪里。它可能是 `y` 的盒子、函数的返回地址，甚至是 `ptr` 自己的盒子。

我们不知道这里会发生什么，并不仅仅是因为我们还没有学到会发生什么——而是因为 C 的规则给了编译器很大的自由来决定如何在内存中布局变量。一个编译器可能在 `x` 后面放置一份数据，而另一个编译器可能在 `x` 后面放置其他数据。事实上，同一个编译器在给定不同的命令行选项改变优化级别时，也可能改变它在内存中排列变量的方式。

我们会把所有具有未定义行为的代码（例如这段代码）视为**错误**。因此，如果你手工执行这段代码，当执行 `ptr = ptr + 1;` 时，你应该把 `ptr` 的值改为仅记作 `&x+1`，而不是任何有效的箭头。如果你随后解引用一个没有有效指向盒子的指针，你应该停下来，宣布你的代码坏了，然后去修复它。我们要注意，仅仅对指针执行算术，使它们不指向有效盒子，本身并不是错误——只有在不知道指针指向什么的情况下解引用它才是问题。我们可以在这段代码之后立即执行 `ptr = ptr - 1;`，并确定地知道 `ptr` 又指向 `x` 了。我们也可能只是在循环末尾越过一个有效的盒子序列，但不使用那个无效的指针值。我们通常不会做这些事情，你应该知道什么是可接受的编码实践，什么不是。
