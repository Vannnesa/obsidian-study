# Principles of Writing Recursive Code
# 编写递归代码的原则

之前我们学到，在把步骤翻译成代码时，一个复杂的步骤应该翻译成对函数的调用。如果你还没有一个执行所需任务的函数，那么你就在完成当前函数之后去写那个函数。编写递归函数实际上只是这个原则的一个特例：我们需要调用的函数恰好就是我们正在写的那个函数。如果我们愿意接受这个函数在完成时会正确工作，那么它正是我们需要使用的。

此时，许多新手程序员会被递归看似“**魔法**”的特性弄糊涂：如果你可以直接调用你正在写的函数，那为什么不直接写：

```c
int factorial_broken(int n) {
  return factorial_broken(n);
}
```

当然，如果计算机能在我们第一个例子中弄明白函数调用自身的“魔法”，它在这里也能施展同样的魔法。

当然，递归实际上并不是魔法。在我们第一个 `factorial` 例子中，我们可以手工执行 `factorial(3)` 并得出正确答案。如果我们尝试执行 `factorial_broken(3)`，我们实际上**永远得不到答案**。相反，我们会**无限递归**——也就是说，`factorial_broken(3)` 只会调用 `factorial_broken(3)`，后者又只会调用 `factorial_broken(3)`，如此永远继续下去。手工执行这段代码，我们会很快意识到问题并停下来。另一方面，计算机不会推理，会继续遵循我们的指令，直到被某种东西阻止——要么是内存耗尽无法再创建栈帧，要么是用户终止程序。

相反，让我们通过考察这两个函数之间的一些关键区别，来更好地理解递归。一个关键区别是，第一个函数是通过遵循**七步法**编写程序得到的，而递归调用对应于我们在尝试解决问题时**实际做过的事情**。相比之下，`factorial_broken` 函数相当于说：“看，计算阶乘的方法就是计算阶乘。”这样的陈述在告诉你如何执行所需任务方面相当无用——尽管它倒很适合这个笑话：“**要写出正确的递归函数，你只需要写出正确的递归函数。**”

第二个区别是，`factorial` 函数有一个**基准情况**（base case）——一种它可以在不调用自身的情况下给出答案的条件——此外还有**递归情况**（recursive case）——函数调用自身的时候。在这个特定函数中，基准情况是 `n <= 0`——函数直接返回 `1`，不再做进一步工作。

正确 `factorial` 函数的另一个重要方面是，递归调用总是**朝着基准情况推进**。在这个特定例子中，每当 `factorial` 调用自身时，它使用的参数值都比自己的小：`factorial(3)` 调用 `factorial(2)`，后者调用 `factorial(1)`，后者调用 `factorial(0)`。
