# Format String Attacks
# 格式字符串攻击

一个可能导致安全漏洞的字符串错误是**格式字符串攻击**（format string attacks）。回想一下，`printf` 接受一个**格式字符串**（一个包含 `%` 符号以表示格式转换的字符串，例如 `%d` 用于转换十进制整数），然后接受适当数量的其他参数作为要转换的值。只要用户可能以某种方式影响格式字符串，使其能够引入额外的格式转换，就会出现**格式字符串漏洞**。

举个简单的例子，假设有一个 `readAString()` 函数可以从用户那里读取一个字符串。考虑以下有漏洞的代码，它试图读取一个字符串然后打印出来：

```c
// 坏代码：不要这样做！
char * input = readAString();
printf(input);
```

如果攻击者输入一个包含 `%` 符号的字符串，就可能导致程序以它不应该的方式运行。注意，上面代码中对 `printf` 的调用使用从用户读取的输入作为**格式字符串**。即使没有任何参数供格式说明符转换，`printf` 也不会被阻止。如果用户输入包含 `%` 转换，`printf` 会到这些参数本该所在的位置取数据，按指示格式化它们，并打印出来。至少，攻击者可以通过在他的输入中放置 `%d` 或 `%s` 格式说明符，让程序**泄露数据**。

这种攻击泄露什么信息，取决于 `printf` 寻找那些额外参数的位置中驻留着什么信息。让这个漏洞更糟的是，`printf` 有一个格式说明符 `%n`，它会把到目前为止打印的字符数**写入**由作为相应参数传入的 `int *` 所指定的内存位置。聪明的攻击者可以利用这个格式转换以恶意方式修改程序的内存，改变其行为，并可能执行任意代码。

使用 `printf` 处理来自用户的字符串输入（或可能受用户影响的输入）的正确方式是使用 `%s` 转换：

```c
// 正确代码
char * input = readAString();
printf("%s", input);
```

注意，如果你的格式字符串不是字面量，并且你没有格式参数（即格式字符串是 `printf` 的唯一参数），`gcc` 会给你一个警告；然而，如果有其他参数，它就不会警告你。这种行为看起来可能奇怪，但存在是有充分理由的。如果你没有任何要转换的内容，应该对字符串使用 `"%s"`。然而，有时你有一个参数，并且想要计算格式字符串。例如，以下代码是没问题的：

```c
const char * fmt = "%d\n";
if (printInHex) {
  fmt = "%x\n";
}
printf(fmt, someNumber);
```

这里，我们确定格式字符串要么是 `%d\n`（以十进制打印数字），要么是 `%x\n`（以十六进制打印数字），两者都可以用于打印 `someNumber`（我们假设它是一个 `int`）。然而，每当我们编写计算格式字符串的代码时，都必须谨慎，确保用户不能以恶意方式影响它。

格式字符串漏洞属于一类更大的安全缺陷，即程序使用了**未净化的输入**（unsanitized inputs）。更一般地说，如果程序使用字符串时某些字符具有特殊含义，它必须注意从用户读取的输入中**移除或转义**那些字符。对于 `printf` 的格式字符串，这些特殊字符是 `%` 符号。如果我们想让用户控制格式字符串，那么只有在（且仅当）我们首先净化字符串的情况下才能安全地这样做——遍历它并修改 `%` 符号以移除其特殊含义（即，移除它们或把它们转换为 `%%`——打印字面百分号的格式说明符）。然而，对于 `printf`，没有理由采取这种方法——更简单（因此更不容易出错）的做法是直接使用 `%s` 说明符来按字面打印字符串。如果我们需要以依赖用户的方式使用格式说明符，我们的代码应该自己构建格式字符串。

然而，在其他一些情况下，我们可能希望从用户读取字符串，并把它包含在字符具有特殊含义的上下文中。两个最常见的情况是传递给**命令 shell** 的命令，以及传递给**数据库**的信息。

命令 shell 认为许多字符是特殊的，但一个特别危险的是反引号 `` ` ``——反引号内的文本会作为它自己的命令执行。假设我们的程序从用户读取一些输入，并把它作为参数传递给一个 shell 命令——也就是说，它执行 `someCommand stringFromUser`。如果恶意用户输入 `` `rm -rf *` ``，那么命令 shell 会执行反引号展开，并运行命令 `rm -rf *`，这会删除当前目录中的所有文件。虽然这个命令具有破坏性，但一个更阴险的用户可以找到更好的命令来执行——那些让他能够访问系统以获取和/或修改信息的命令。

类似的问题也可能发生在数据库使用不当时，程序把 SQL 命令作为字符串传递给数据库。我们不会深入 SQL 的细节，但想象一下，我们可以在不完全理解它们的情况下说明这一点。假设程序想运行命令 `SELECT * from Users WHERE name='strFromUser'`，其中 `strFromUser` 是从用户读取的字符串（例如，你要求他们输入用户名，他们输入了它）。如果我们不小心，用户可能输入一个 `'`（终止用于匹配 `name` 的字面量），以及一个 `;` 来结束当前命令，后面跟着他自己选择的任意命令。这样的漏洞允许攻击者随意修改数据库中的信息。网络漫画 xkcd 有一幅关于这个主题的精彩漫画：http://xkcd.com/327/ 。

注意，净化输入是一项必须小心执行的任务。一个只能捕获一半情况的净化函数，几乎比完全不净化好不了多少——聪明的攻击者会尝试所有可能的特殊字符，最终找到那个允许她攻破你系统的字符。每当你需要净化输入时，首先要做的最好的事情是检查是否已经有专家编写的现成函数可用。例如，一些数据库接口有**预处理语句**（prepared statements），允许你在 SQL 查询中用 `?` 代替各种输入，把值绑定到那些输入，然后数据库库确保没有输入净化问题。
