# Fancier make Options
# 更高级的 make 选项

回想一下，`make` 的输入是一个 `Makefile`，其中包含一个或多个规则，指定如何从其**先决条件**（prerequisites，即它所依赖的文件）生成一个**目标**（target）。规则由目标说明、一个冒号，以及先决条件文件列表组成。先决条件列表之后是一个换行符，然后是从先决条件重新构建该目标所需的任何命令。这些命令可以跨多行；然而，每一行都必须以 **TAB 字符**开头（多个空格不行，意外地用空格代替 TAB 通常是 `Makefile` 问题的来源）。

当你运行 `make` 时，可以指定要构建的特定目标（如果不指定，`make` 使用 `Makefile` 中的第一个目标作为默认目标）。要构建目标，`make` 首先检查它是否是最新的。检查目标是否最新，首先需要通过可能重新构建每个先决条件来确保它们都是最新的。当 `make` 遇到一个存在且本身不是任何规则目标的文件时，这个过程就到底了。这样的文件就是最新的。

一旦确保了一个目标所依赖的所有文件都是最新的，`make` 就检查目标本身是否需要（重新）构建。首先，`make` 检查目标文件是否存在。如果不存在，就必须构建它。如果目标文件已经存在，`make` 将其**最后修改时间**（所有主流文件系统都跟踪它）与规则中指定的每个先决条件的最后修改时间进行比较。如果任何依赖项比目标文件更新，那么目标就是过时的，必须重新构建。注意，如果在这个过程中任何先决条件被重新构建了，那么该文件将被修改得比目标更晚，从而迫使目标被重新构建。

## An example
## 一个例子

为了更具体一点，让我们看一个 `Makefile` 的具体例子：

```make
myProgram: oneFile.o anotherFile.o
    gcc -o myProgram oneFile.o anotherFile.o
oneFile.o: oneFile.c oneHeader.h someHeader.h
    gcc -std=gnu99 -pedantic -Wall -c oneFile.c
anotherFile.o: anotherFile.c anotherHeader.h someHeader.h
    gcc -std=gnu99 -pedantic -Wall -c anotherFile.c
```

在这个 `Makefile` 中有三个目标：`myProgram`、`oneFile.o` 和 `anotherFile.o`。如果我们只输入 `make`，那么 `make` 将尝试（重新）构建 `myProgram`，因为它是文件中的第一个目标，因此是默认目标。这个目标依赖于 `oneFile.o` 和 `anotherFile.o`，所以 `make` 要做的第一件事就是制作 `oneFile.o` 目标（就像我们输入了 `make oneFile.o` 一样）。

`oneFile.o` 依赖于一个 `.c` 文件和两个 `.h` 文件，它们都不是其他规则的目标。因此，`make` 不需要重新构建它们。如果它们还不存在，`make` 会给出这样的错误：

```text
make: *** No rule to make target 'oneHeader.h', needed by 'oneFile.o'.  Stop.
```

假设这三个 `.c`/`.h` 文件都存在，`make` 会检查 `oneFile.o` 是否存在，或者这三个文件中是否有任何一个比它更新。如果是，那么 `make` 将通过运行指定的 `gcc` 命令来重新构建该文件。如果 `oneFile.o` 已经存在并且比相关的源文件更新，那么构建它就不需要做任何事情。

处理完 `oneFile.o` 之后，`make` 对 `anotherFile.o` 做类似的处理。完成后，它检查是否需要构建 `myProgram`（也就是说，`myProgram` 不存在，或者它依赖的任何一个目标文件比它更新）。如果是，它运行指定的 `gcc` 命令（该命令将链接目标文件并生成名为 `myProgram` 的二进制文件）。如果不是，它会输出消息：

```text
make: 'myProgram' is up to date.
```

观察一下，由于这个过程的工作方式，如果你更改了 `oneFile.c` 中的代码，那么两个目标文件中只有一个会被重新编译（`oneFile.o`），然后程序会被重新链接。另一个目标文件（`anotherFile.o`）不需要重新编译。虽然对于两个文件来说这看起来差别不大，但如果项目有 50 个文件，并且使用了大量优化编译，那么重新编译全部 50 个和只重新编译一个之间的差别将是非常明显的时间量。

## Variables
## 变量

我们编写示例 `Makefile` 的方式有很多复制粘贴——这是我们在做任何事情时都想避免的。特别是，我们可能注意到在许多地方都有相同的编译器选项。如果我们想更改这些选项（例如，打开优化，或添加调试标志），我们就必须在每个地方都改。相反，我们更愿意把编译器选项放在一个**变量**中，并在每个相关规则中使用该变量。例如，我们可以把前面的例子改成下面这样：

```make
CFLAGS=-std=gnu99 -pedantic -Wall
myProgram: oneFile.o anotherFile.o
    gcc -o myProgram oneFile.o anotherFile.o
oneFile.o: oneFile.c oneHeader.h someHeader.h
    gcc $(CFLAGS) -c oneFile.c
anotherFile.o: anotherFile.c anotherHeader.h someHeader.h
    gcc $(CFLAGS) -c anotherFile.c
```

这里，我们定义了一个变量 `CFLAGS`，把它设置为我们想要的编译标志。然后我们通过在规则中把变量名放在 `$()` 内来使用它。注意，对 `Makefile` 的更改不会自动使使用它们的目标过时，所以如果你在更改后只输入 `make`，它们不一定会用新标志重新构建（不过你可以让它们都依赖于 `Makefile`）。

## Clean
## 清理

`Makefile` 中常见的一个目标是 `clean` 目标。`clean` 目标有点不同，因为它实际上并不创建一个名为 `clean` 的文件（因此它被称为“**伪目标**”，phony target）。相反，它是一个用于删除已编译程序、所有目标文件、所有编辑器备份（`*.c~ *.h~`）以及任何其他你可能认为是杂乱文件的的目标。这个目标用于强制整个程序重新构建（例如，在你在 `Makefile` 中更改了各种编译标志之后），或者如果你只是需要清理目录，只留下源文件（例如，如果你要打包或压缩源文件以便分发给别人）。

我们可以像下面这样向 `Makefile` 添加一个 `clean` 目标：

```make
.PHONY: clean
clean:
    rm -f myProgram *.o *.c~ *.h~
```

注意 `.PHONY: clean` 告诉 `make`，`clean` 是一个伪目标——我们实际上并不期望它创建一个名为 `clean` 的文件，也不希望如果已经存在一个名为 `clean` 的文件就认为它是最新的并跳过其命令（由于没有先决条件，如果它存在，它就会被认为是最新的）。如果我们想要其他伪目标，我们会把它们都列出来，就像它们是 `.PHONY` 目标的先决条件一样（例如 `.PHONY: clean depend`）。

一般来说，你应该在你的 `Makefile` 中添加一个 `clean` 目标，因为大多数人会期望有一个，而且它可能非常有用。

## Generic rules
## 通用规则

当我们使用一个变量来保存编译标志时，我们的示例 `Makefile` 稍微改进了。然而，我们的 `Makefile` 仍然存在大量重复，如果我们有超过几个源文件，维护起来会很痛苦。如果你看看我们写的内容，我们把每个 `.c` 源文件编译成目标文件时做的事情几乎是一样的。每当我们发现自己重复自己时，就应该有更好的方法。

在 `make` 中，我们可以编写**通用规则**。通用规则让我们可以指定，我们希望能够从 `(something).c` 构建 `(something).o`，其中我们用百分号（`%`）表示 `something`。作为第一步，我们可能会这样写（注意 `#` 表示到行末的注释）：

```make
# 一个好的开始，但我们失去了对头文件的依赖
CFLAGS=-std=gnu99 -pedantic -Wall
myProgram: oneFile.o anotherFile.o
    gcc -o myProgram oneFile.o anotherFile.o
%.o: %.c
    gcc $(CFLAGS) -c $<
.PHONY: clean
clean:
    rm -f myProgram *.o *.c~ *.h~
```

这里，我们把每个目标文件的两条规则替换成了一条通用规则。它指定了如何从同名但扩展名为 `.c` 而不是 `.o` 的文件生成以 `.o` 结尾的文件。在这个规则中，我们不能写出源文件的实际名称，因为它会随规则的每个实例而变化。相反，我们必须使用特殊的内置变量 `$<`，`make` 会把它设置为规则的第一个先决条件的名称（在这个例子中是 `.c` 文件的名称）。

然而，我们现在引入了一个严重的问题。我们使得目标文件不再依赖于相关的头文件。如果我们更改了一个头文件，那么 `make` 可能不会重新构建所有相关的目标文件。这样的错误可能导致奇怪且令人困惑的 bug，因为一个目标文件可能期望旧布局的数据，但代码现在会以不同布局传递数据。我们可以让每个目标文件依赖于每个头文件（通过写 `%.o : %.c *.h`），然而，这种方法太过头了——当我们更改头文件时，我们肯定会重新构建所有需要的东西，因为我们会重新构建每个目标文件，即使我们只需要重新构建少数几个。

我们可以通过向 `Makefile` 添加额外的依赖信息，以更好的方式修复这个问题：

```make
# 这解决了问题
CFLAGS=-std=gnu99 -pedantic -Wall
myProgram: oneFile.o anotherFile.o
    gcc -o myProgram oneFile.o anotherFile.o
%.o: %.c
    gcc $(CFLAGS) -c $<
.PHONY: clean
clean:
    rm -f myProgram *.o *.c~ *.h~
oneFile.o: oneHeader.h someHeader.h
```

这里，我们仍然有通用规则，但我们也单独指定了额外的依赖。尽管看起来我们有两条规则，`make` 理解我们只是在提供额外的依赖信息，因为我们没有指定任何命令。如果我们确实指定了命令，它们将取代那些目标的通用规则。

当然，手工管理所有这些依赖信息会既繁琐又容易出错。程序员必须弄清楚每个源文件传递包含的每个文件，并随着代码变化保持信息最新。相反，有一个名为 `makedepend` 的工具，它会编辑 `Makefile`，把所有这类信息放在末尾。在最简单的用法中，`makedepend` 接受所有源文件（即所有 `.c` 和/或 `.cpp` 文件）作为参数，并编辑 `Makefile`。它还可以接受各种选项，例如 `-I path` 告诉它在指定路径中查找包含文件。详情请参见 `man makedepend`。

## Built-in generic rules
## 内置通用规则

有些通用规则非常常见，它们被内置到 `make` 中，我们甚至不需要写它们。你可能已经猜到，从同名 `.c` 文件构建 `.o` 文件非常常见，因为这是 C 程序员最常做的事情。因此，如果我们对用于这种模式的内置通用规则满意，我们甚至不需要显式地写 `%.o: %.c` 规则。

我们可以通过使用 `make -p` 来查看所有规则（包括内置的和 `Makefile` 指定的）。这样做也会像往常一样构建默认目标——如果我们想避免构建任何东西，可以执行 `make -p -f/dev/null`，使用特殊文件 `/dev/null` 作为我们的 `Makefile`（从 `/dev/null` 读取会立即得到文件结束，所以结果是一个没有规则的 `Makefile`，因此它不会做任何事情）。

如果我们使用 `make -p` 来探索从 `.c` 文件构建 `.o` 文件的内置规则，我们会发现：

```make
%.o: %.c
# commands to execute (built-in):
    $(COMPILE.c) $(OUTPUT_OPTION) $<
```

理解这条规则需要我们查看 `COMPILE.c` 和 `OUTPUT_OPTION` 的定义，它们也包含在 `make -p` 的输出中：

```make
COMPILE.c = $(CC) $(CFLAGS) $(CPPFLAGS) $(TARGET_ARCH) -c
OUTPUT_OPTION = -o $@
```

默认情况下，`CFLAGS`（C 编译器标志）和 `CPPFLAGS`（C 预处理器标志），以及 `TARGET_ARCH`（指定目标架构的标志）都是空的。默认情况下，`CC`（C 编译器命令）是 `cc`（根据系统配置，它可能是也可能不是 `gcc`）。这些变量（或任何其他变量）的默认值可以通过在我们的 `Makefile` 中指定它们的值来覆盖。注意 `OUTPUT_OPTION` 中的 `$@` 是一个特殊变量，它是当前目标的名称（很像 `$<` 是第一个先决条件的名称）。

所有这些听起来可能有点复杂，但它基本上归结为：默认规则是 `cc -c -o something.o something.c`，我们可以覆盖具体细节来得到我们想要的行为，同时仍然使用默认规则。也就是说，我们可能会使用以下 `Makefile`：

```make
CC = gcc
CFLAGS = -std=gnu99 -pedantic -Wall
myProgram: oneFile.o anotherFile.o
    gcc -o myProgram oneFile.o anotherFile.o
.PHONY: clean depend
clean:
    rm -f myProgram *.o *.c~ *.h~
depend:
    makedepend anotherFile.c oneFile.c
# DO NOT DELETE
```

这里，我们指定了要使用 `gcc` 作为 C 编译器（`CC`），并指定了我们想要的 `CFLAGS`。现在，当我们尝试从 C 文件编译目标文件时，默认规则将导致：

```bash
gcc -std=gnu99 -pedantic -Wall -c -o something.o something.c
```

你还应该注意，我们添加了另一个伪目标 `depend`，它用我们正在使用的两个 C 源文件运行 `makedepend`。`# DO NOT DELETE` 行及其下面的所有内容是我运行 `make depend` 时 `makedepend` 添加到我们 `Makefile` 中的。注意，如果我们重新运行 `makedepend`（最好通过 `make depend`），它会查找这一行来告诉它在哪里删除旧的依赖信息并添加新信息。

## Built-in functions
## 内置函数

我们的 `Makefile` 看起来越来越像可以在大型项目中使用的了，但我们仍然在几个地方手工列出了源文件和目标文件。如果我们添加一个新的源文件，但忘记更新 `makedepend` 命令行，那么当我们运行 `make depend` 时，就不会得到该文件的正确依赖。同样，我们可能会忘记在正确的位置添加目标文件（例如，如果我们把它添加到编译命令行，但没有添加到整个程序的依赖中，我们可能在需要时不会重新构建那个目标文件）。

我们可以通过使用 `make` 的一些内置函数来自动计算当前目录中的 `.c` 文件集合，然后从该列表生成目标目标文件列表，从而解决这些问题。`make` 中函数调用的语法是 `$(functionName arg1, arg2, arg3)`。我们可以使用 `$(wildcard pattern)` 函数来生成当前目录中的 `.c` 文件列表：`SRCS = $(wildcard *.c)`。然后我们可以使用 `$(patsubst pattern, replacement, text)` 函数将 `.c` 结尾替换为 `.o` 结尾：`OBJS = $(patsubst %.c, %.o, $(SRCS))`。完成这些后，我们可以在 `Makefile` 中使用 `$(SRCS)` 和 `$(OBJS)`：

```make
CC = gcc
CFLAGS = -std=gnu99 -pedantic -Wall
SRCS=$(wildcard *.c)
OBJS=$(patsubst %.c,%.o,$(SRCS))
myProgram: $(OBJS)
    gcc -o $@ $(OBJS)
.PHONY: clean depend
clean:
    rm -f myProgram *.o *.c~ *.h~
depend:
```

此时，我们有了一个可以在大型项目中使用的 `Makefile`。当我们添加源文件或在现有源文件中包含新头文件时，唯一需要做的就是运行 `make depend` 来更新依赖信息。除此之外，我们可以用 `make` 构建项目，它只会重新编译所需的文件。

不过，我们可以再高级一点。在真实项目中，我们可能希望构建代码的**调试版本**（无优化，加上 `-ggdb3` 打开调试信息——关于调试的更多信息见下一个模块），以及一个运行更快的**优化版本**（编译器努力工作以改进它生成的指令，但这些变换通常使调试相当困难）。我们可以在调试标志和优化标志之间来回更改 `CFLAGS`，并记得每次切换时 `make clean`。然而，我们也可以把 `Makefile` 设置成用不同的名称构建调试和优化的目标文件及二进制文件：

```make
CC = gcc
CFLAGS = -std=gnu99 -pedantic -Wall -O3
DBGFLAGS = -std=gnu99 -pedantic -Wall -ggdb3 -DDEBUG
SRCS=$(wildcard *.c)
OBJS=$(patsubst %.c,%.o,$(SRCS))
DBGOBJS=$(patsubst %.c,%.dbg.o,$(SRCS))
.PHONY: clean depend all
all: myProgram myProgram-debug
myProgram: $(OBJS)
    gcc -o $@ -O3 $(OBJS)
```

现在，如果我们 `make`，我们会得到 `myProgram`（优化版本）和 `myProgram-debug`（为调试编译的版本）。

## Parallelizing computation
## 并行化计算

`make` 的一个有用特性，尤其是在现代多核系统上，是能够**并行运行独立任务**。如果你给 `make` 加上 `-j` 选项，它会请求尽可能多地并行运行任务。你可能希望限制任何给定时间并行任务的数量，你可以通过给 `-j` 选项指定一个数字来实现（例如，`make -j8` 最多并行运行 8 个任务）。在大型项目上，这可能会显著影响构建所需的时间。

## ……还有更多
