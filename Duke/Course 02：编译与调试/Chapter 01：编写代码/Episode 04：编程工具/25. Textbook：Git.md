# Git

虽然在编程的早期阶段，版本控制（revision control）——使用软件来跟踪代码的多个版本，并让多个开发者轻松协作——可能看起来并不重要，但它是专业开发（甚至更大规模的学术开发）中至关重要的一部分。有许多不同的流行版本控制系统，但它们大多共享一些共同原则。我们将重点关注 `git`，它目前是最流行的工具，并且功能相当丰富。我们强烈建议你尽早学习版本控制，并把它作为软件开发（以及你所做的大多数其他事情）标准实践的一部分。这里我们将介绍一些高级功能和使用的动机，但详细内容请参考 git 书籍：  
https://git-scm.com/book/en/v2

## Past versions
## 过去的版本

大多数版本控制系统的基本原理是：你把工作**提交**（commit）到版本控制系统中，然后它会保留你该版本工作的**快照**。提交时，你写一条**日志条目**（log entry），描述你做了什么。之后，你可以查看日志，并在需要时回到工作的旧版本。例如，如果你决定重写一段代码来改进它，结果却发现反而破坏了程序，你可以回到之前可工作的版本。

针对这个问题，“**新手工具**”式的做法是保留工作的副本，并手工管理它们。你可能会想：“好吧，我可以在开始之前复制所有代码，然后如果需要就用那个副本。”如果你有意识地意识到自己即将进行有风险的代码重写，你可能会采取这种做法。然而，如果你开始修改代码，之后才意识到麻烦呢？如果你使用版本控制系统，就应该**定期提交**，因此过去会有良好的修订版本。此外，如果你手动定期复制，你会发现很难手工管理所有副本。

像 `git` 这样的版本系统还有处理过去版本的出色工具。例如，`git` 有一个名为 `bisect` 的命令，可以让你搜索过去是在哪里弄坏东西的。假设我知道某个功能 6 个月前还能工作，但今天运行一些测试后意识到该功能坏了。我想回去准确找出哪个版本破坏了这个功能，看看那个版本改了什么，然后修正代码。`bisect` 命令让 `git` 帮我搜索第一个出问题的版本。具体来说，`bisect` 在修订版本之间进行**二分搜索**（因此得名），以找到问题发生的位置。你可以通过告诉 `git` 它访问的每个修订版本是好是坏来手动引导搜索，也可以提供一个 shell 脚本，让 `git` 判断修订版本是否正确或有坏，从而全自动执行搜索。

版本控制不仅限于代码，事实上，它对任何大型协作项目（甚至只是小规模管理你自己的数据）都非常有用。为了给出 `bisect` 的一个具体例子，我们用 `git` 对本课程所基于的书的**所有材料**进行版本控制——包括 LaTeX 源码、代码示例、动画和视频录制。其中一个动画被无意中删除了，我们需要从最近的版本恢复它。写一个 shell 脚本来测试该文件是否存在，然后运行 `git bisect`，在几秒钟内就找到了删除该文件的修订版本，并让我们从上一个修订版本恢复了它（并确保我们拥有最新版本！）。

## Collaboration
## 协作

当你参与一个拥有数百个源文件和几十名开发者的软件项目时，如何让每个人都了解最新的源代码？来回通过电子邮件发送文件会是一场噩梦。即使只有两个人参与一个项目，管理开发者之间的变更也是首要问题。

像 `git` 这样的版本控制系统支持**推送**（pushing）——把你的更改发送到另一个仓库（位于另一台计算机上）——和**拉取**（pulling）更改——从另一个仓库获取最新版本。如果你尝试推送自己的更改，但没有与另一个仓库保持同步，`git` 会要求你先拉取，这样你就不会意外覆盖别人的更改。当你拉取时，`git` 会小心确保你的更改与远程更改集成。

如果你拉取，并且（自上次推送到该仓库以来）没有对自己的仓库做任何更改，`git` 会简单地把你的仓库更新到最新版本。如果你做了更改，`git` 会尝试把你的更改与远程更改**合并**（merge）。如果你更改了不同的文件，或同一文件的不同部分，`git` 通常会**自动处理合并**。然而，如果 `git` 无法自动合并，它会指出需要你注意的问题，并要求你在把更改推回去之前修复它们。

## Multiple versions of the present
## 当前的多个版本

像 `git` 这样的版本控制工具不仅让你回到过去的版本，还通过一个称为**分支**（branches）的功能，让你保留多个不同的“当前”版本。要理解为什么你可能想要多个“当前”版本，想象你正在开发一个大型软件项目，并决定开始添加一个复杂的新功能。添加这个功能将花费你和你的五人团队四周时间完成。工作一周后，当前发布的软件版本中发现了一个关键问题，必须尽快修复。

这种情况非常适合使用分支。开发团队可以维护一个分支 `production`，其中包含准备发布的代码。对 `production` 分支的唯一更改是那些准备部署的更改。另一个 `development` 分支可以用于活跃的开发——添加新功能、测试它们等。在上述情况中，`development` 分支就是团队添加新的复杂功能的地方。

这些分支如何帮助？被分配修复 `production` 代码中 bug 的开发者可以**检出**（checkout）那个分支（在那个“当前”版本上工作），而其他开发者可以继续在 `development` 分支上工作。事实上，这位开发者可以（也应该）创建一个新分支（我们称之为 `bugfix`）来处理 bug 修复。然后开发者可以把更改提交到 `bugfix`，如果其他开发者也需要处理那个修复，他们可以切换到该分支。当 bug 修复完成时，它可以被合并回 `production` 分支，把更改纳入生产软件。

同时，新功能的开发在 `development` 分支上继续。当 bug 修复完成时，它也可以被合并到 `development` 分支。同样，当新功能开发完成并准备发布时，它们可以被合并回 `production` 分支。每当这些合并发生时，`git` 会执行与合并从另一个仓库拉取的更改时类似的操作——如果它能自动处理，就自动处理；否则要求开发者弄清楚如何解决冲突。

注意，这只是一个规模较小的动机示例。如果我们真的在开发一个大型软件，几乎肯定需要比上面描述的更多分支。我们可能有不同的开发者在并行处理不同的功能，并希望用分支来管理这些更改的组合。我们可能还需要用于不同测试阶段或其他目的的分支。
