# Black Box Testing
# 黑箱测试

大多数人首先想到的测试方法是**黑箱测试**（black box testing）。在黑盒测试中，测试者只考虑函数的**预期行为**——而不是任何实现细节——来设计测试用例。之所以叫这个名字，是因为测试者无法访问实现细节——函数的实现被视为一个“**黑盒**”，测试者不能往里看。

黑盒测试并不意味着测试者临时想几个用例就完事了。相反，测试者——其目标是**精心设计可能暴露错误的测试用例**——应该思考：从函数行为来看，哪些情况**容易出错**。例如，假设你需要测试一个对整数列表求和的函数。不看代码，你会想到哪些测试用例？

我们可能从简单的测试用例开始，测试代码的基本功能——例如，看看当输入为 `{1,2,3,4,5}` 时函数是否给出答案 `15`。然而，我们还应该设计更困难的测试用例，特别是那些测试**边界情况**（corner cases）的用例——即需要与其他情况不同特定行为的输入。在这个例子中，我们可能用**空列表**（即没有数字的列表）测试，看是否得到答案 `0`。我们可能确保测试包含负数的列表，或者包含许多非常大数字的列表。你应该思考这些测试用例可能暴露哪些错误。

注意，我们能够为这个假设问题思考出好的测试用例，而**无需**经过步骤 1–5。实际上，你可以在开始解决问题**之前**就为它想出一组黑盒测试。有些程序员提倡**测试先行**（test-first）的开发方法。一个好处是，如果你在开始之前就写好了全面的测试套件，你就不太可能在实现代码后**敷衍测试**。另一个好处是，通过提前思考边界情况，你在开发和实现算法时**更不容易犯错**。
