# Compiler Errors
# 编译器错误

编译器是一个相当复杂的程序。它的第一个任务是读取你的程序源代码，并根据 C 的规则“理解”你的程序——这个任务称为**解析**（parsing）。为了让编译器解析你的程序，源代码必须具有正确的**语法**（syntax）（正如我们在课程 1 中讨论的）。如果你的代码语法不正确，编译器会打印一条错误消息，并尝试继续解析，但可能会被之前的错误搞糊涂。例如，下面的代码有一个错误——第 5 行的 `int x = 3` 后面缺少分号：

```c
#include <stdio.h>
#include <stdlib.h>
 	
int main(void) {
  int x = 3
  int y = 4;
	printf("%d\n", x + y);
  return EXIT_SUCCESS;
}
```

然而，编译这段代码会导致**两个**错误：

```text
err1.c: In function 'main':
err1.c:6: error: expected `,' or `;' before `int'
err1.c:7: error: `y' undeclared (first use in this function)
err1.c:7: error: (Each undeclared identifier is reported only once
err1.c:7: error: for each function it appears in.)
```

第一个错误（`expected `,' or `;' before `int'`）正确地指出了我们代码的问题——在编译器看到第 6 行开头的 `int` 之前，我们缺少一个分号（它应该在第 5 行末尾，但编译器在看到下一个单词之前不知道出了问题）。下一个错误（`'y' undeclared`）实际上并不是代码的另一个问题，而是编译器被第一个错误搞糊涂的结果——缺少分号导致它把 `y` 的声明误解为前一个语句的一部分，因此它无法识别后面代码中的 `y`。

编译器错误可能会让新手程序员感到困惑和沮丧。处理它们的一个关键规则是：**尝试按顺序修复它们，从第一个到最后一个**。如果你发现除第一个之外的错误消息让你困惑，先修复第一个错误，然后重新编译代码，看看那个错误是否消失——它可能只是编译器被较早错误搞糊涂的结果。

**处理编译错误：技巧 1** 记住，编译器可能会被较早的错误搞糊涂。如果后面的错误令人困惑，先修复第一个错误，然后在尝试修复它们之前重新编译。

处理编译器错误时的另一个困惑来源是，错误消息可能没有很好地描述问题。编译器会尽力描述问题，但可能会错误地猜测你试图做什么，或者提到你不熟悉的可能性。例如，如果我们在前面的缺少分号问题上有一个稍微不同的变体：

```c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
  int x
  int y;
  x = 3;
  y = 4;
  printf("%d\n", x + y);
  return EXIT_SUCCESS;
}
```

这里的错误仍然是第 5 行 `x` 的声明后缺少分号，然而，编译器给出了以下错误消息：

```text
err2.c: In function 'main':
err2.c:6: error: nested functions are disabled, use -fnested-functions to re-enable
err2.c:6: error: expected `=', `,', `;', `asm' or `__attribute__' before `int'
err2.c:7: error: `x' undeclared (first use in this function)
err2.c:7: error: (Each undeclared identifier is reported only once
err2.c:7: error: for each function it appears in.)
```

这些错误消息可能看起来相当吓人，因为它们提到了几个我们还没见过的语言特性（而且这些特性都与问题无关）。这里的第一个错误消息实际上**完全不相关**，除了它所在的行号是对的。编译器首先猜测我们可能试图使用一个非标准的语言扩展（某个特定编译器允许在语言中使用的额外特性），它允许我们在另一个函数内部写一个函数。这个扩展默认是禁用的，编译器认为我们可能想启用它——它在试图提供帮助，尽管它错了。一般来说，如果一条错误消息引用了完全陌生的东西，很可能是编译器糊涂了，或者提供了与你试图做的事情无关的建议。

**处理编译错误：技巧 2** 如果错误消息的某些部分完全陌生，试着忽略它们，看看错误消息的其余部分是否讲得通。如果讲得通，就试着用讲得通的部分来理解和修复你的错误。如果讲不通，就在 Google 上搜索那些令人困惑的部分，看看它们是否有任何相关性。

看下一条错误消息，我们看到它在同一个行号（6）上，所以编译器可能试图就同一个问题给我们更多或不同的信息。这里，虽然有一些陌生的东西（比如 `asm` 或 `__attribute__`），但如果我们忽略这些，错误消息的其余部分就讲得通。也就是说，如果错误消息是下面这样，我们就能理解：

```text
err2.c:6: error: expected `=', `,', or `;' before `int'
```

编译器告诉我们，它期望在第 6 行到达单词 `int` 之前看到一个等号、逗号或分号。在这个情况下，我们缺少一个分号，但编译器也在建议其他可能性（例如，如果我们写的是 `int x = 3;`，就可能有一个 `=`）。它提供的 `asm` 和 `__attribute__` 建议也可能是选项，但它们是非常高级的语言特性，我们不会涉及。

处理错误消息时的另一个困惑来源是，编译器可能不会**立即**注意到错误。只要源代码似乎遵守 C 的语法规则，编译器就假定一切都是正确的，即使它的解析与你本意不一致。在下面的代码中，实际的错误是第 9 行缺少一个右花括号：

```c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
  for (int i = 0; i < 10; i++) {
    for (int j = 0; j < 10; j++) {
      printf("%d\n", (i+3) * (j+4));
    }
 
  return EXIT_SUCCESS;
```

然而，编译器不会立即识别出这个错误。在 `for` 循环内部有一个 `return` 语句在语法上是有效的。它后面第 11 行的右花括号——程序员本意是 `main` 的结尾——也是合法的，但编译器把它解析为第一个 `for` 循环的结尾。然后编译器在到达文件末尾时发现有些不对劲，`main` 的函数体还没有结束，于是报告错误为：

```text
err3.c: In function 'main':
err3.c:11: error: expected declaration or statement at end of input
```

**处理编译错误：技巧 3** 程序员编辑器非常擅长帮助你找到不匹配的花括号和圆括号。大多数编辑器会根据它所处嵌套层级自动缩进代码，并且当你的光标在一对括号之一上时，会显示匹配的括号。使用这类功能可能是找到不匹配花括号和圆括号错误的最简单方法。

一旦编译器解析了你的程序，它会对程序进行**类型检查**（type-check）。类型检查程序涉及确定每个表达式的类型（包括其中的子表达式），并确保它们与使用方式兼容。它还涉及检查函数被传递的参数数量和类型是否正确。编译器会为在这个过程中发现的任何问题生成错误消息。

关于修复编译器错误的另一个重要注意事项是：有时修复一个错误会让编译器继续前进，从而产生**更多**错误。那些对自己的第一个错误修正没有信心的新手程序员可能会撤销修复，以为他们把情况弄得更糟了，即使修复可能是正确的——额外的错误只是因为编译器在过程中走得更远了。

**处理编译错误：技巧 4** 对你错误的修复要有信心。如果你不理解哪里错了以及如何修复，就去弄清楚并确定，而不是随机地改来改去。

一旦编译器完成对代码错误的检查，它会将其翻译成**汇编**——即执行程序所说内容所需的各个机器指令。你可以要求编译器**优化**你的代码——对它进行变换，使生成的汇编运行得更快——方法是指定 `-O` 选项，后面跟上你想要的优化级别。程序通常在测试和调试时以**无优化**方式编译（代码变换使程序非常难以调试），然后在准备发布/使用时重新以优化方式编译。通常，用 `gcc` 编译的真实程序在优化时会用 `-O3` 编译。`gcc` 提供了各种其他选项来在更细的粒度上控制优化，然而，它们超出了本专项课程的范围。我们严格关心编写能工作的代码，所以在本专项课程的任何练习中，你都不需要费心使用 `-O` 标志。
