# White Box Testing
# 白盒测试

另一种测试方法是**白盒测试**（white box testing）。与黑盒测试不同，白盒测试涉及检查代码来设计测试用例。白盒测试中的一个考虑因素是**测试覆盖**（test coverage）——描述你的测试用例对代码不同行为的覆盖程度。

注意，虽然白盒测试和黑盒测试不同，但它们并不是互斥的，而是**互补的**。人们可能会先形成一组黑盒测试用例，实现算法，然后创建更多测试用例以达到所需的测试覆盖水平。

```c
int aFunction(int a, int b, int c) {
  int answer = 0;
  if (a < b) {
    answer = b - a;
  }
  if (b < c) {
    answer = answer * (b - c);
  }
  else {
    answer = answer + 42;
```

我们将讨论三个层次的测试覆盖：**语句覆盖**（statement coverage）、**决策覆盖**（decision coverage）和**路径覆盖**（path coverage）。为了说明每种覆盖类型，我们将使用上面展示的（人为设计的）代码示例。

**语句覆盖**意味着函数中的每个语句都被执行。在我们的例子中，如果我们只使用一个测试，`a=1, b=2, c=3`，我们就没有语句覆盖。具体来说，这个测试用例（单独）没有执行代码的第 10 行（`else` 的主体）。我们缺乏覆盖表明我们没有充分测试函数——它有一些行为我们的测试用例没有执行到。

语句覆盖是一个最低起点，但如果我们想很好地测试代码，我们可能想要一个更强的覆盖指标。要看到语句覆盖的不足，注意我们还没有测试任何 `a < b` 测试求值为假的情况——也就是说，我们没有进入 `if` 语句主体（第 4 行）的情况。

更强的覆盖级别是**决策覆盖**——其中所有可能的决策结果都被执行。对于布尔测试，这意味着我们构造一个表达式求值为真的测试用例，以及另一个求值为假的测试用例。如果我们有 `switch/case` 语句，我们必须为 `case` 语句中的每个选择构造至少一个测试用例，再加上一个用于 `default` 情况的测试用例，即使它是隐式的——也就是说，即使我们没有写它，它的行为就像我们写了 `default: break;`。

为了更全面地理解决策覆盖，将其可视化会有所帮助。为了可视化决策覆盖，我们需要理解**控制流图**（control flow graph，常缩写为 “CFG”）的概念。控制流图是一个有向图（数学意义上的），其节点是**基本块**（basic blocks，即方框），其边表示控制流箭头可以移动的可能方式（即箭头）。基本块是必须按“全有或全无”方式执行的连续语句序列；执行箭头不能跳入或跳出基本块的中间。CFG 显示控制流箭头如何从一个基本块移动到下一个。

上图显示了前面图中示例函数的控制流图。第一个基本块只有一条箭头进入，表明它是起点——执行箭头只能通过调用函数到达它。这个第一个基本块有两个语句：`answer` 的声明/初始化，以及测试 `a < b` 的 `if` 语句。基本块在这里结束，因为执行箭头可以去两个地方——由离开这个块的两条边表示。最后一个块没有箭头离开它；当执行箭头移动到该块末尾时，在这个函数内没有别的地方可去。此时，函数完成并返回其答案。注意，我们一次为一个函数绘制 CFG。我们也可以绘制执行箭头如何在函数之间移动；那称为**调用图**（call graph）。

决策覆盖对应于拥有一组覆盖图中**每条边**的测试用例。在我们的图中，如果 `a < b` 为真，我们将走离开第一个块的左边（对应于进入 `if/else` 的 “then” 子句）。如果为假，我们将走右边，跳过这个子句，由于没有 `else` 子句，直接到下一个 `if` 语句。这第二条边——表示当 `a < b` 为假时执行箭头的路径——在上图中用红色突出显示，因为它代表了我们的测试用例到目前为止在决策覆盖方面的不足。

我们可以通过添加一个测试用例来获得这个函数的决策覆盖，其中执行箭头遍历控制流图的这条边——或者换种说法，`a < b` 决策求值为假。这个测试用例的一个例子是 `a=5, b=2, c=1`。

更强的测试覆盖类型是**路径覆盖**。要实现路径覆盖，我们的测试用例必须跨越控制流图中所有可能的有效路径（沿着箭头方向）。上图显示了通过我们示例控制流图的四条路径，并根据我们的测试用例覆盖它们的情况进行了颜色编码。注意有一条路径（用红色显示）我们还没有覆盖。这条路径对应于 `a < b` 为假，但 `b < c` 为真的情况。给我们决策覆盖的测试用例分别测试了这些条件中的每一个，但没有一个测试同时测试两者——即执行会沿着红色路径走的情况。我们可以添加另一个测试用例（例如 `a=5, b=22, c=99`）来获得路径覆盖。

此时你可能会想：“为什么我们有所有这些测试覆盖级别？”以及“我如何为正在做的事情选择正确的覆盖级别？”软件工程师定义并讨论多个测试覆盖级别，因为更高的覆盖级别让我们对代码的正确性更有信心，但代价是需要更多测试用例。虽然我们的示例对于讨论的三个覆盖级别只需要 2、3 和 4 个测试用例，但它是一个简单（且人为设计）的代码片段。控制流图中的路径数量随条件选择数量呈**指数增长**——如果我们有 6 个连续的 `if/else` 语句，那么控制流图中有 64 条可能路径。如果我们将 `if/else` 语句数量从 6 增加到 16，那么路径数量增长到 65536——相当多！

那么你如何选择正确的测试覆盖级别？与许多事情一样，答案是“视情况而定”。这个决定的第一个方面是“你需要对代码有多大信心？”如果你在步骤 4 中手工对算法进行初步测试（并且一旦将其翻译成代码，就会测试实现的算法），那么语句覆盖是一个合理的选择。在这里，测试更多用例相当耗时（你是手工做的），而且你以后会做更多测试用例（一旦它被翻译成代码并编译，你可以让计算机运行测试）。

相比之下，如果你在测试一个关键软件，并且测试完成后就会部署，那么仅实现语句覆盖将**远远不够**。在这里，你可能想要瞄准超过最低限度的目标来实现路径覆盖。不幸的是，没有任何数量的测试能够确保代码正确——它只能增加我们对它正确的信心。如果你要求代码绝对正确，你必须**形式化证明**它（这超出了本课程的范围）。
