# Asserts
# 断言

在任何形式的测试中，不仅检查最终结果，还检查系统在执行过程中**不变量**（invariants）是否得到维护，都可能很有用。**不变量**是在程序中给定点上（应该）始终为真的性质。当你知道代码中某个给定点应该为真的不变量时，你可以编写一个 `assert` 语句来检查它为真。`assert(expr);` 检查 `expr` 是否为真。如果为真，则什么也不发生，执行正常继续。然而，如果 `expr` 为假，它会打印一条消息，说明断言失败，并**中止程序**——无论程序在哪里，都立即终止它。

举个例子，回想之前某个练习问题中的 `printFactors` 函数。我们可以添加一些 `assert` 语句来表达算法的**不变量**：

```c
void printFactors(int n) {
  if (n <= 1) {
    return;
  }
  int p = 2;
  while (!isPrime(n)) {
    assert(isPrime(p));      // p 应该始终是素数
    assert(p < n);           // p 应该始终小于 n
    if (n % p == 0) {
      printf("%d * ", p);
```

这里，我们添加了两个 `assert` 语句。第一个在第 7 行，检查 `p` 是素数（使用我们的 `isPrime` 函数）。这个事实在这里应该始终为真——如果不是，我们的算法就坏了（我们可能最终打印出数字的非素数因子，这是不正确的）。这样的错误怎么会发生？一种可能是 `nextPrimeAfter` 中的 bug——这是我们编写的、用于查找某个素数之后的下一个素数的辅助函数。另一种可能是我们意外地以不打算的方式修改了 `p`。当然，如果我们的代码是正确的，这两种情况都不会发生，`assert` 什么也不做，但关键是在我们确实犯错时帮助我们。

第二个 `assert` 检查我们算法的另一个不变量：在这个循环内部，`p` 应该始终小于 `n`（想想为什么……）。与第一个 `assert` 一样，我们希望它没有效果——只是检查表达式始终为真——但如果有什么不对，它会帮助我们检测问题。

注意，`assert` 语句是这样一个原则的例子：如果我们的程序有错误，我们希望它**快速失败**（fail fast）——也就是说，我们宁愿程序在错误发生后尽快崩溃。程序在错误发生后运行得越久，它就越可能给出错误答案，调试也越困难。理想情况下，当我们的程序有错误时，我们会有一个 `assert` 在错误发生后立即失败，准确指出问题是什么以及在哪里。

在几乎所有情况下，给出错误答案（由于未检测到的错误）都比程序检测到情况并崩溃**糟糕得多**。要看到这种权衡，考虑计算导弹发射轨迹的软件。如果这样的软件有错误，你宁愿它给出错误的发射指令，还是打印一条发生错误的消息并中止？

许多新手和中级程序员担心 `assert` 会拖慢程序。一般来说，这种减速**可以忽略不计**，尤其是在快速的现代计算机上。在许多情况下，1–2% 的性能根本不重要——你真的在乎是 0.1 秒还是 0.11 秒得到答案吗？然而，在性能敏感的情况下，每一点速度都很重要。对于这些情况，你可以向编译器传递 `-DNDEBUG` 选项，以在优化代码中关闭 `assert`。对于所有其他情况，保持它们活跃通常是可取的。注意，性能关键代码是专家程序员的领域，他们也对底层硬件有深入理解——这远远超出了本专项课程的范围。
